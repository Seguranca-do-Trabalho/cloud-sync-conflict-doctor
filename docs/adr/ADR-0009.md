# ADR-0009 — GUI: Avalonia UI

- **Status:** Accepted
- **Date:** 2026-08-22
- **Decided by:** Architect (card T01)

## Context

§15: the GUI is the main product — consumer-grade app appearance, flow: choose folder → scan → summary → duplicates → conflicts → compare → quarantine → confirmation. Market requirements: direct sales outside the Microsoft Store **and** Store presence (§28). ADR-0001 fixed .NET 8. Alternatives considered: Avalonia UI, WinUI 3, WPF.

| Criterion (weight for this product) | Avalonia 11 | WinUI 3 | WPF |
|---|---|---|---|
| Consumer app outside Store, signable single EXE | ✅ trivial self-contained | ⚠️ runtime/WinAppSDK dependencies complicate direct distribution | ✅ mature |
| Microsoft Store path | ✅ packages as desktop bridge | ✅ native | ✅ desktop bridge |
| Modern consumer look without extra effort | ⚠️ good with own Fluent theme | ✅ native Fluent | ❌ dated; requires third-party toolkit |
| MVVM/testability with Doctor.Core | ✅ | ✅ | ✅ |
| Stack risk (evolution, Linux tooling for CI) | ✅ cross-platform, headless CI simple | ❌ Windows only, heavy tooling | ✅ |
| Fits §52 (no overengineering) | ✅ single framework | ⚠️ entire WinAppSDK for one window | ✅ |

WinUI 3 has the most native look but ties distribution to WinAppSDK — real friction for single-EXE direct sales (explicit commercial requirement). WPF solves distribution but delivers a dated appearance, requiring third-party kits to look consumer-grade. Avalonia covers both paths (direct EXE + Store) with a single framework and lower operational risk.

## Decision

**Avalonia UI 11** in `src/Doctor.Gui`, MVVM, referencing only `Doctor.Core`. Fluent theme as base with own identity. GUI consumes the report schema (ADR-0003); has no second logic engine (§13).

Criteria that sealed the choice, in order: (1) dual distribution without forking code; (2) lower stack risk for a small product; (3) headless testability in CI; (4) consumer-grade look achievable without extra third parties.

## Consequences

- Visually unambiguous safety (§37): quarantine action never shares affordance with comparison; explicit confirmation before moving.
- UI prototype (card T06) validates the §15 flow before full implementation.
- If Store later requires specific MSIX packaging, that is a packaging layer (EPIC 14/16) and does not change the framework choice.
