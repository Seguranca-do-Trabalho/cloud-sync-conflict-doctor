# ADR-0009 — GUI: Avalonia UI

- **Status:** Aceito
- **Data:** 2026-08-22
- **Decidido por:** Architect (card T01)

## Contexto

§15: a GUI é o produto principal — aparência de aplicativo de consumidor, fluxo escolher pasta → escanear → resumo → duplicatas → conflitos → comparar → quarentena → confirmação. Requisitos de mercado: venda direta fora da Microsoft Store **e** presença na Store (§28). ADR-0001 fixou .NET 8. Alternativas consideradas: Avalonia UI, WinUI 3, WPF.

| Critério (peso p/ este produto) | Avalonia 11 | WinUI 3 | WPF |
|---|---|---|---|
| App de consumidor fora da Store, EXE único assinável | ✅ self-contained trivial | ⚠️ dependências de runtime/WinAppSDK complicam distribuição direta | ✅ maduro |
| Caminho Microsoft Store | ✅ empacota como desktop bridge | ✅ nativo | ✅ desktop bridge |
| Look moderno de consumidor sem esforço extra | ⚠️ bom com tema Fluent próprio | ✅ Fluent nativo | ❌ datado; requer toolkit de terceiros |
| MVVM/testabilidade com Doctor.Core | ✅ | ✅ | ✅ |
| Risco de stack (evolução, tooling Linux p/ CI) | ✅ multiplataforma, CI headless simples | ❌ só Windows, tooling pesado | ✅ |
| Cabe no §52 (sem overengineering) | ✅ um framework só | ⚠️ WinAppSDK inteiro para uma janela | ✅ |

WinUI 3 tem o visual mais nativo, mas amarra distribuição ao WinAppSDK — atrito real para venda direta de EXE único (requisito comercial explícito). WPF resolve distribuição mas entrega aparência datada, exigindo kit de terceiros para parecer consumidor. Avalonia cobre os dois caminhos (EXE direto + Store) com um único framework e menor risco operacional.

## Decisão

**Avalonia UI 11** em `src/Doctor.Gui`, MVVM, referenciando apenas `Doctor.Core`. Tema Fluent como base com identidade própria. A GUI consome o schema do relatório (ADR-0003); não possui segundo motor de lógica (§13).

Critérios que selaram a escolha, em ordem: (1) distribuição dual sem bifurcar código; (2) menor risco de stack para um produto pequeno; (3) testabilidade headless no CI; (4) visual de consumidor atingível sem terceiros extras.

## Consequências

- Segurança visualmente inequívoca (§37): ação de quarentena nunca compartilha affordance com comparação; confirmação explícita antes de mover.
- Protótipo de UI (card T06) valida o fluxo do §15 antes da implementação plena.
- Se a Store futuramente exigir empacotamento MSIX específico, isso é camada de packaging (EPIC 14/16) e não altera a escolha de framework.
