# ADR-0005 — Hashing BLAKE3: parcial 64 KiB início+fim, completo só no fim da cascata

- **Status:** Aceito
- **Data:** 2026-08-22
- **Decidido por:** Architect (card T01)

## Contexto

§4 exige BLAKE3 explícito no relatório; §8 manda hash parcial dos primeiros + últimos 64 KiB apenas para sobreviventes do agrupamento; §9 reserva o hash completo aos candidatos que passarem pelo nível 2; §12 exige cache incremental com chaves estáveis.

## Decisão

1. Pacote NuGet **`Blake3`**, versão pinada em `Directory.Packages.props`. Saída sempre hexadecimal minúscula; campos do relatório: `algorithm = "BLAKE3"`, `hash_version = 1`.
2. `hash_version = 1` fixa o esquema **inteiro**: algoritmo, tamanho de janela e ordem de concatenação. Alterar qualquer um desses elementos implica bump de `hash_version` e invalidação total do cache.
3. Hash parcial (esquema v1):
   - `size ≤ 128 KiB` (131.072 bytes): leitura sequencial única do arquivo inteiro em um único hasher BLAKE3.
   - `size > 128 KiB`: uma única abertura; alimenta o hasher com a janela `[0, 64 KiB)` e depois `[size − 64 KiB, size)`, nesta ordem.
   - Os mesmos bytes nunca são lidos duas vezes para o mesmo hash.
4. Hash completo: BLAKE3 integral, executado somente em membros de grupo com mais de um sobrevivente do L2 (§10: minimizar `bytes_read_full`).
5. Arquivo vazio (`size == 0`): hash parcial = hash completo = BLAKE3 de zero bytes; nenhuma leitura.
6. **Gate de segurança:** `IHasher` recebe `FileEntry` e lança `PlaceholderReadException` se `IsPlaceholder == true`. Invariante automatizada: `placeholder_bytes_read == 0` (§6, §21).
7. Integridade TOCTOU: `size` + `mtime` capturados em L0 são revalidados após a leitura; divergência ⇒ um recálculo; persistindo ⇒ registrado como erro parcial (exit 3 do ADR-0008), nunca silenciado nem "melhor estimado".

## Consequências

- Contrato formal em `docs/contratos.md` (`IHasher`).
- O cache (ADR-0006) armazena hash parcial e completo sob chave validada por `size`/`mtime`/`algorithm`/`hash_version`.
