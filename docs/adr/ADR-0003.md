# ADR-0003 — Schema do relatório v1 e regra de determinismo

- **Status:** Aceito
- **Data:** 2026-08-22
- **Decidido por:** Orquestrador (card T03)

## Contexto

§3 exige que a mesma árvore produza relatório **byte-a-byte idêntico**, independentemente de ordem de enumeração, threads ou hash maps. §13 manda um único modelo de domínio alimentando JSON e GUI.

## Decisão

Schema JSON versionado:

```json
{
  "report_schema_version": 1,
  "algorithm": "BLAKE3",
  "hash_version": 1,
  "generated_from": { "root_path": "<caminho escaneado>", "scan_started_utc": "...", "scan_finished_utc": "..." },
  "telemetry": {
    "files_enumerated": 0, "files_skipped": 0, "files_placeholder": 0,
    "files_partial_hashed": 0, "files_full_hashed": 0,
    "bytes_read": 0, "bytes_read_partial": 0, "bytes_read_full": 0,
    "placeholder_bytes_read": 0
  },
  "groups": [ ... ],
  "identical_duplicates": [ ... ],
  "real_conflicts": [ ... ],
  "placeholders": [ ... ]
}
```

Regras de determinismo (obrigatórias, testadas):

1. Serialização sempre sobre estruturas ordenadas por **caminho em bytes UTF-8** (não locale).
2. Empate em qualquer decisão: `mtime` → `size` → `path`. Nunca "first seen".
3. `scan_started_utc/finished_utc` ficam fora das listas; nenhuma lista contém campo incidental de tempo.
4. Teste CI: 3 scans na mesma árvore sintética com ordens de enumeração diferentes → arquivos de saída idênticos byte por byte.

## Consequências

- GUI não tem segundo motor de lógica; consome exatamente este schema.
- Trocar hash/algoritmo = bump de `hash_version`; trocar formato = bump de `report_schema_version`.
